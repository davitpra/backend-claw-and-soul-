# Refresh Token Rotation

This document explains the Refresh Token Rotation security feature implemented in the authentication system.

## 🔐 What is Token Rotation?

Token Rotation is a security practice where:
1. Each time a refresh token is used, it's immediately invalidated
2. A new refresh token is generated and returned
3. The old token can never be used again

## 🎯 Security Benefits

### 1. Prevents Replay Attacks
If an attacker steals a refresh token, they can only use it once. After that, it becomes invalid.

### 2. Detects Token Theft
If a token is used twice, we know something is wrong:
- The legitimate user used it → Got new token
- Attacker tries to use the old token → **DETECTED!**

### 3. Automatic Response to Threats
When token reuse is detected, the system:
- Revokes ALL tokens for that user
- Forces re-authentication
- Logs the security event

### 4. Tokens Hashed in Database
Refresh tokens are **never stored in plain text**. Before writing to or reading from the database, the raw JWT is hashed with SHA-256:

```typescript
// auth.service.ts
private hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}
```

This means a database breach does **not** expose valid tokens — an attacker would need the raw JWT (which only ever lives in the httpOnly cookie) to make a request.

## 🔄 How It Works

```
User makes request with refresh token (Token A)
        ↓
Backend SHA-256 hashes Token A → looks up hash in DB
        ↓
Backend validates Token A
        ↓
Backend revokes Token A (sets isRevoked = true)
        ↓
Backend generates new tokens (Token B + new access token)
        ↓
Stores SHA-256 hash of Token B in DB
        ↓
Returns Token B (raw) to user via httpOnly cookie
        ↓
Token A hash is now permanently revoked in DB
```

## 🚨 Token Reuse Detection

If someone tries to use an already-revoked token:

```
Attacker tries to use Token A (already used)
        ↓
Backend hashes Token A → finds record with isRevoked = true
        ↓
🚨 SECURITY ALERT: Token reuse detected!
        ↓
Revoke ALL tokens for this user
        ↓
User must log in again
```

> **Important**: Revoked tokens are kept in the database for **30 days** before being deleted by the daily cleanup job. This window ensures that reuse detection can fire even if the legitimate user has logged in again since the token was rotated. See [Automatic Cleanup](#-automatic-cleanup).

## 📊 Token Lifecycle

```
Login/Register
    ↓
Token Created — hash stored in DB (Active)
    ↓
Token Used for Refresh → New Token Created (hash stored) → Old Token hash set to isRevoked=true
    ↓
Token Expires (7 days) → deleted by per-login or daily cleanup
    ↓
Revoked Token → kept 30 days for reuse detection, then deleted by daily cleanup
```

## 🧹 Automatic Cleanup

The system uses two layers of cleanup to keep the token table lean.

### Per-Login Cleanup (inside `generateTokens`)
Every time new tokens are generated (login, register, or refresh), the system deletes **only date-expired** tokens for that user:

```typescript
// auth.service.ts - cleanupExpiredTokens (called inside generateTokens)
await this.prisma.refreshToken.deleteMany({
  where: {
    userId,
    expiresAt: { lt: new Date() },  // Only expired by date
  },
});
```

Revoked tokens are intentionally **not** deleted here — they must remain in the DB so that reuse detection can trigger `revokeAllUserTokens` if the old token is presented again.

### Daily Cleanup (3 AM)
- Deletes all date-expired tokens (belt-and-suspenders)
- Deletes revoked tokens older than **30 days**

```typescript
// auth-cleanup.service.ts
@Cron(CronExpression.EVERY_DAY_AT_3AM)
async cleanupExpiredTokens() { ... }
```

### Per-User Session Limits
- Maximum **5 active sessions** per user
- When the limit is exceeded, the oldest sessions are revoked

### Manual Cleanup
```typescript
// auth-cleanup.service.ts
await authCleanupService.manualCleanup();
```

## 💻 Implementation Details

### Backend Code

```typescript
// auth.service.ts - hashToken helper
private hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}

// auth.service.ts - refreshToken method
async refreshToken(refreshToken: string) {
  // 1. Validate JWT signature/expiry
  const payload = await this.jwtService.verifyAsync(refreshToken, { secret: '...' });

  // 2. Look up by hash — never query the raw token
  const storedToken = await this.prisma.refreshToken.findUnique({
    where: { token: this.hashToken(refreshToken) },
  });

  // 3. Check for reuse (SECURITY)
  if (!storedToken || storedToken.isRevoked) {
    if (storedToken) {
      // isRevoked=true → reuse detected → revoke everything
      await this.revokeAllUserTokens(storedToken.userId);
    }
    throw new UnauthorizedException('Invalid refresh token');
  }

  // 4. Revoke old token
  await this.prisma.refreshToken.update({
    where: { id: storedToken.id },
    data: { isRevoked: true },
  });

  // 5. Generate new tokens and store hash
  const tokens = await this.generateTokens(payload.sub, payload.email, payload.role);

  return tokens; // raw tokens returned; only hashes in DB
}
```

## 📱 User Session Management

Users can view and manage their active sessions:

### View Active Sessions
```
GET /api/auth/sessions
```

Returns list of active sessions with:
- Session ID
- Creation date
- Expiration date

> Note: raw tokens are never returned — only the session ID (UUID), which is safe to expose.

### Revoke Specific Session
```
POST /api/auth/sessions/revoke/:tokenId
```

### Revoke All Other Sessions
```
POST /api/auth/sessions/revoke-all
```

This is useful when:
- User suspects unauthorized access
- User wants to log out from all other devices
- User lost a device

## 📈 Best Practices

1. **Monitor Logs**: Watch for token reuse warnings — they indicate a possible attack
2. **Never store raw tokens**: Always hash before writing to DB (`SHA-256`)
3. **Keep revoked tokens around**: Do not delete revoked tokens immediately — they are the evidence for reuse detection
4. **Set session limits**: Don't allow unlimited sessions per user (current limit: 5)
5. **Regular cleanup**: The daily cron keeps the token table clean without destroying reuse evidence prematurely
6. **Audit trail**: All token-related security events are logged
